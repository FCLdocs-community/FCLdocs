Java 移植

Minecraft Java 版是一个标准的 Java 程序，它需要一个完整的 Java 虚拟机（JVM） 才能运行。Android 系统虽然用 Java/Kotlin 开发应用，但它的应用运行时（ART）只接受安卓专用的 dex 字节码，无法直接运行 Minecraft 使用的标准 Java 字节码。因此，手机启动器要解决的第一个问题就是：把一个标准的 JVM 带到 Android 上。

为什么选择 OpenJDK​

OpenJDK 是 Oracle 主导的开源 Java 实现，采用 GPL 协议发布。选择它有两个原因：

  1. 开源可修改：可以把源码改成能在 Android 上编译、运行的版本；
  2. 与官方环境一致：Minecraft 官方启动器使用的就是 OpenJDK 系的 JVM，兼容性最好。

Oracle 早年曾开展过 OpenJDK Mobile 项目，验证了「JVM 可以运行在 Android 上」这条路线，PojavLauncher 团队在此基础上完成了工程化。

移植工作包含什么​

PojavLauncher 团队的相关仓库是 android-openjdk-build-multiarch（构建脚本）和 openjdk-multiarch-jdk8u、jdk17u、jdk21u 等（修改后的 OpenJDK 源码）。移植主要包含三部分工作：

1. 适配 C 标准库

桌面 Linux 程序依赖 glibc，Android 使用自家的 Bionic libc。OpenJDK 的 C/C++ 代码中有大量按 glibc 编写的系统调用，需要逐一改写为 Bionic 提供的接口，否则无法在 Android 上编译和链接。

2. 交叉编译

在电脑上使用 Android NDK，为四种 CPU 架构分别编译出 JVM：

目录适用设备
bin-arm32 位 ARM 手机（已很少见）
bin-arm64绝大多数现代手机
bin-x86 / bin-x86_64模拟器、部分平板与 Chromebook

这也是 FCL 内置的每个 Java 运行时都按架构分包的原因。

3. 裁剪

去掉 Minecraft 用不到的组件（桌面 Swing 界面、大部分调试工具等），只保留 JVM 核心、类库与 AWT 替代实现，将体积从数百 MB 压缩到几十 MB。

最终产物是一个可以在 Android 进程内加载的 libjvm.so。

内置运行时与版本对应关系​

FCL 的 APK 内打包了四个版本的 JRE（源码位于 FCL/src/main/jreAssets/app_runtime/java/），首次启动时解压到应用私有目录 runtime/java/ 下：

运行时对应 Minecraft 版本
jre81.16.5 及更早（1.12.2 以下必须，1.13–1.16.5 默认）
jre171.17 ~ 1.20.4
jre211.20.5 ~ 1.21.x
jre2526.1 及以后（26.x 均要求 Java 25）
关于 26.x 的新版本号

从 26.1 起，Minecraft Java 版改用了新的版本号格式（2025 年 12 月 2 日宣布），版本号不再以 1.x 递增，同时最低 Java 要求提升到 Java 25。

每个运行时目录内有 version 文件记录版本号，升级 APK 后启动器会对比版本，不一致则重新解压覆盖——这是更新 FCL 后首次启动变慢的原因。

除内置运行时外，FCL 也支持在「版本设置」中导入自行下载的 JRE，前提是对应架构、针对 Android 编译。

启动时的加载流程​

启动游戏时（源码 FCLauncher.setUpJavaRuntime()），启动器依次执行：

  1. 读取 JRE 目录下的 release 文件，确认该运行时编译目标架构，定位 lib/<架构>/ 目录；
  2. 按顺序 dlopen（加载进当前进程内存）JVM 的各依赖库：
libjli.so → libjvm.so → libfreetype.so → libverify.so
→ libjava.so → libnet.so → libnio.so → libawt.so → libfontmanager.so
→ 递归扫描 JRE 目录，加载其余全部 .so
  1. 调用 com.oracle.dalvik.VMLauncher.launchJVM(args)，在启动器进程内启动 JVM，由它执行拼装好的 Minecraft 启动命令。
为什么要 dlopen？

Android 的安全策略限制应用直接加载数据目录中的 so 文件。启动器先通过 native 层将 JVM 库加载进内存（dlopen），JVM 内部后续按需加载依赖库时就能复用已有句柄。游戏日志中成段的 "DLOPEN" 记录即来源于此。

Java 8 的特殊处理​

代码中对 JDK 8 有一系列专门处理（isJDK8() 判断、/jre 子目录、server/client 两种 JVM 目录）：

  • 目录结构不同：JDK 8 时代 JRE 与 JDK 分离，目录中多一层 jre/；
  • AWT 不同：1.12.2 及更早的版本直接用 AWT 绘制界面，FCL 通过 Caciocavallo 桥（内置 caciocavallo/caciocavallo17 运行库）把 AWT 绘制结果映射到 Android Surface 上；
  • 性能：Java 8 没有 17+ 的新 GC 等特性，运行老版本时启动与帧生成都更慢，这是版本本身决定的。

移植后的 JVM 与桌面版有何差异​

  • ✅ 版本、模组加载器（Forge/Fabric/NeoForge 等）、整合包均按标准 JVM 的方式运行；
  • ✅ JIT 编译、垃圾回收等核心机制完整保留；
  • ⚠️ 性能受手机散热与调度策略影响，长时间高负载会降频；
  • ⚠️ 少数依赖 JVM 内部 API 的模组需要启动器额外注入补丁（FCL 内置 MioLibPatcher 处理此类需求）。
